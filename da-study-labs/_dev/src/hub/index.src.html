When only one tool fits

Each approach has a job it does far better than the others, and some jobs only one of them can do. Slide the data size to see where each tool stops, then try the two cases below it.

Assumptions behind these estimates
  • Rough orders of magnitude for a simple sum per key, not benchmarks. Real speeds depend on hardware, data format and query.
  • Excel: hard limit of 1,048,576 rows per sheet, about 500 thousand rows per second.
  • Python loop: one laptop, about 1 million rows per second, about 50 million rows fit in memory.
  • SQL on one database server: about 20 million rows per second, up to about 5 billion rows.
  • Spark cluster: about 20 seconds to start, then about 300 million rows per second across machines.
Excel wins
Test how a price change moves the margin, then show it to a colleague.

Editing a cell recomputes everything on screen and anyone can audit it by clicking. A script or query has to be re-run, and few business users can read it.

Python loop wins
Simulate a balance month by month, where each month depends on the last and the stop point is not known.

Step-by-step state with a dynamic stop is natural in a loop. SQL needs a recursive query, Excel needs rows you extend by hand, and Spark would run one job per iteration.

SQL wins
Revenue by region for the last 90 days from a table that already lives in the warehouse.

The query runs where the data is and reads only the partitions it needs. Exporting to Excel or Python would copy the data first.

Spark wins
Aggregate 2 billion log lines stored as files in object storage.

Too big for Excel and for one laptop, and there may be no database to load it into. Spark reads the files in parallel across a cluster.

How Excel thinks

      
Excel sits between the loop and the set. You never write a loop, but you also work cell by cell, with every intermediate result on screen.

      

        
The grid is the program
Data, formulas and results share one sheet. You can click any cell and see its value, which makes steps easy to check. SQL and Spark keep intermediate tables hidden unless you select them.

        
One formula, filled down
A formula in one cell, copied down a column, is a column expression applied to every row. That is close to set thinking. The difference is that it points at cells by position (B2, $C$2:$C$11) instead of by column name.

        
Helper columns, not pipelines
Each step becomes a new column or range next to the data. This is simple to audit, but refreshing with new data often means pasting and re-extending ranges by hand.

        
Where it stops
A sheet holds at most 1,048,576 rows and recalculates as you edit. When the data outgrows it, the same logic moves over: SUMIFS becomes GROUP BY, XLOOKUP becomes JOIN.

Habits to unlearn in Spark

      
These are the three most common ways a loop mindset slows a Spark job down.

      

        

          
Pulling data to the driver

          
Avoid


for row in df.collect():
    tax = row["amount"] * 0.1

          
Prefer


df.withColumn("tax",
    F.col("amount") * 0.1)

          
collect() moves every row to one machine. The column expression runs on all partitions in parallel.

        

        

          
Python UDF for simple math

          
Avoid


@F.udf("double")
def add_tax(x):
    return x * 1.1
df.withColumn("total", add_tax("amount"))

          
Prefer


df.withColumn("total",
    F.col("amount") * 1.1)

          
A UDF sends each value between the JVM and Python. Built-in expressions stay inside Spark, where the optimizer can see them.

        

        

          
withColumn inside a loop

          
Avoid


for c in cols:
    df = df.withColumn(c, F.upper(c))

          
Prefer


df.select([F.upper(c).alias(c)
           for c in cols])

          
Each withColumn adds a layer to the query plan. One select describes the whole change at once.
